# Doc-to-Markdown benchmark: scoring

`score.mjs` scores three outputs per corpus file (`packforai.document`, `packforai.compact`, `markitdown`) against the frozen ground truth in `corpus/ground-truth/`:

```
node score.mjs corpus <outDir> > results.json     # the summary table goes to stderr
node --test score.test.mjs                        # 86 tests
```

The normative rules are the `normalization` and `metric_definitions` blocks that every `results.json` carries. This file explains why they changed. Every rule applies in the same way to all three candidates, and every normalization applies to the ground truth too. The ground-truth files were not changed.

## 1.2.0 changes

The evidence comes from `results/run1-2026-11-24/verification.json`, an independent adversarial check of run 1 scored with 1.1.0 (`results.json`, `summary.txt`). Run 1 rescored with 1.2.0 is in `results-scorer-1.2.0.json` and `summary-scorer-1.2.0.txt`, next to the 1.1.0 files.

**1. Compound hyphen across a line break (text_recall, order_score).** In 1.1.0, `40,000-` at a line end followed by `pound` was normalized to `40,000- pound`. So the must_contain phrase "applicants importing typical 40,000-pound loads …" was missed in both PackForAI outputs of `pub-fedreg-2024-31144.pdf` (text_recall 0.929, 13/14). The ground-truth notes say this hyphen is a true compound. Rule now: for must_contain phrases and ordered anchors, on both sides, a hyphen between a letter or digit and a letter loses the space after it (`([\p{L}\p{N}])- (?=\p{L})` becomes `$1-`). Digits count on the left because the evidence case is `40,000-`; a letter-only rule changes nothing in run 1. A split word stays split (`regu-lation` is not `regulation`), so de-hyphenation is still measured. Absent strings do not use this rule, because it would merge the separate entries `com- mercial` and `com-mercial` and count one artefact twice. Run 1: PackForAI document and compact go from 13/14 to 14/14 on fedreg. Nothing else changes.

**2. Absent strings split by other text, with a word boundary.** In 1.1.0 an absent entry counted only as a plain substring. MarkItDown reads two- and three-column pages line by line across the columns. A word broken at a line end then has text from another column between its halves, for example `the com- positions during the evening peak` followed on the next line by `mercial team expects`, and the entry was not counted. verification.json gives `gen-two-column.pdf`: MarkItDown 1 violation vs PackForAI 10, although MarkItDown leaves the same 13 line-end hyphens unjoined. It also gives `pub-fedreg-2024-31144.pdf`: MarkItDown 2/3, with `Destina- tion` split as `Destina- applicable fees …` / `… tion Markets`. 1.1.0 also had no word boundary, so `in- spection` would have matched inside `within- spection`. Rule now: (a) an occurrence of the entry must not start inside a word; (b) a split-word entry `<prefix>- <rest>` is also present when `<prefix>-` starts a word and is followed by a space or the end of the line, and `<rest>` starts a word later on that line or on one of the next 2 non-blank lines. In run 1, `Instal- lation` in MarkItDown's two-column output has its rest 2 lines down (a table row, then a line from the other column). A hyphenated prefix on its own (`pre- and post-war`) does not count, and neither does a rest inside another word (`commercial`). Run 1: two-column MarkItDown goes from 1 to 10 (9 entries via rule (b), each checked by hand against the output lines), fedreg MarkItDown from 2 to 3. PackForAI is unchanged (10 and 3), and srpt stays at 4 for every tool. Totals: MarkItDown 7 → 17, PackForAI 17 → 17.

**3. Table columns that are empty in every row.** In 1.1.0, MarkItDown's tables in `pub-census-ecomm-24q3.pdf` carried a padding column that was empty in every row, header included. In the data fragments no column pairs by header text, so columns pair by position, and the empty column moved every value one column to the right. Table recall was 0.106 (Table 1 7/93, Table 2 7/51); verification.json predicted about 0.67 without the padding. Rule now: each parsed table is scored as written and again without its all-empty columns, and the variant with more matching cells is kept (as written on a tie). The scorer does not always drop the column because the ground truth of `gen-sales.xlsx` keeps an empty spacer column (column E). A converter that reproduced that column faithfully under a title row would pair by position, and dropping the column would shift it. Expected tables are left as they are: dropping column E there would shift PackForAI document and MarkItDown, which both fill that column with a placeholder. Run 1: census MarkItDown goes from 0.106 to 0.666 (40/93 and 46/51). No other file changes.

**3a. Safeguard: a lone shared number does not align two rows.** Without the padding, MarkItDown's table of contents in `pub-srpt-118-226.pdf` put page number `5` under the CBO table's `5` in two rows. That scored 2/23 (table recall 0 → 0.087) for a table MarkItDown never output; verification.json lists "15 tables in output, none of them Table 1". Rule now: in the row alignment, a row pair whose only matching cell is a number (a cell without a letter) does not count, unless that is the only non-empty cell of the expected row. A lone row label such as `Bob` still counts. A stricter "2 matching cells per row" rule was rejected because it would stop crediting a correct label in a row whose value is missing. Run 1: only that file changes, back to 0.

**4. Thousands separators in numeric cells.** In 1.1.0 the expected cells of `gen-sales.xlsx` use Excel's en-US display (`1,200`) and every tool writes `1200`. That cost each tool the same 6 cells (`1,200`, `1,050`, `3,990`, `1,497`, `1,743`, `3,990`). Rule now: a table cell that is a whole number with comma groups of 3 loses those commas, on both sides; sign, decimals, currency and parentheses stay (`$7,560.00` = `$7560.00`, but not `7560`). Text matching (must_contain) keeps separators. Run 1, Q1 Sales / Regions: PackForAI document 0.744 / 0.629 → 0.758 / 0.714 (file 0.686 → 0.736) and MarkItDown 0.626 / 0.629 → 0.640 / 0.714 (0.627 → 0.677). These are the values verification.json predicted.

**5. New secondary metric `spurious_table_cells` (summary column `spur`).** In 1.1.0 no metric counted table syntax built from non-table text. MarkItDown turns justified prose into pipe tables: in two-column, 19 tables with 128 non-empty cells, of which 3 are Table 1 cells; 15 tables in srpt and 16 in fedreg. On two-column its table_precision was still 1.0, because the table picked was a header-only fragment. Rule now: the metric counts the non-empty cells of parsed tables (pipe and CSV) that sit on no ground-truth cell. Every parsed table is aligned with every expected table by the table_recall rules. A cell is on the ground truth when its row is aligned to an expected row, its column is paired with an expected column and that expected cell is non-empty. A cell on the ground truth but with a different value (`7560` for `$7,560.00`) is a wrong value: recall and precision already count it, so it is not counted again here. Everything else counts: tables made of prose, title and caption rows, placeholder headers (`Column 2`, `Unnamed: 1`) and filler such as `NaN` where the expected cell is empty. Fragments of a real table that align with it are not spurious. The value is null when the ground truth lists no table. It does not change table_recall. Caveat: rows of a real table that the ground truth does not list also count. In fedreg, 40 of MarkItDown's 73 are `§51.xx` section numbers from the page-4 redesignation table, which is real but not in the ground truth, mixed into tables with prose from the next column. Run 1 per file: PackForAI document 2 (docx placeholder headers) + 9 (xlsx title row and `Column N` headers) = 11. PackForAI compact 2 (docx). MarkItDown 38 (xlsx title, `Unnamed: N`, `NaN`) + 119 (two-column) + 6 (census header fragments) + 73 (fedreg) + 105 (srpt) = 341. `per_output_table` gives the figure for each parsed table.

**6. CSV text parsed as tables (chosen: parse, not n/a).** In 1.1.0 only GFM pipe tables were parsed. PackForAI compact writes XLSX and CSV sheets as RFC 4180 CSV, with doubled quotes. So `gen-orders.csv` compact scored table recall 0 although it is lossless (verification.json: converted to a pipe table it scores 1.0), and `gen-sales.xlsx` compact scored 0 / 0. Rule now: (1) a fenced block with info string `csv` is a table; (2) outside fences, a paragraph is a table when all its lines, after at most one caption line, are one-line RFC 4180 records with the same field count of 2 or more (2 records or more). Quoted fields keep their commas, and `""` reads as `"`. To stay unambiguous, a line is not a CSV record when it starts with a Markdown block marker, when an unquoted field starts or ends with a space (prose `, `), or when it contains a whitespace-delimited number with comma thousands separators. That last guard is needed: without it, two lines of MarkItDown's two-column output (`B: Tilt-tray sorter 1,450,000 31 a fallback …`) became a false 2×3 CSV table. Parsing was chosen over n/a because every block in run 1 parses unambiguously. Exactly three CSV tables are found, all in PackForAI compact outputs: gen-orders 121×11, gen-sales Q1 Sales 27×9 (its title line is the caption) and Regions 6×6. No other output of any tool yields a CSV table. The compact PPTX output writes table cells one per line, which is not a table and stays 0. Run 1: gen-orders compact goes from 0 to 1 (1251/1251), gen-sales compact from 0 to 0.736, equal to the document output.

**Not changed in 1.2.0.** text_recall still misses phrases that a CSV block holds with doubled quotes: gen-orders compact finds 17/20 (`Harbourside ""Fresh"" Market`). verification.json lists this, but it was not part of this change set.
